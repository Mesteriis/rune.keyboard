# U8 — offline WebView editing acceptance (partial)

The new debug-only WebEditingQaFixture runs in :qa_editor, selected by the fixed
qa_webview_fixture launch flag. It loads one inline textarea document with no
caller-supplied HTML or URL. Network loading, file/content access and DOM storage
are disabled; navigation is refused and resource interception supplies empty
responses. The JavaScript bridge accepts only bounded numeric length/selection
observations. It never sends editor text to the IME or into diagnostic status.
The fixture removes the bridge and detaches/destroys its WebView on Activity exit.

Actual WebView InputConnections are wrapped to count the same six payload APIs:
before/after cursor, selected/extracted/surrounding text and snapshot. These
wrappers observe the channel, not JavaScript's own numeric view of its editor.
The tests check zero counters both after setup and after commands. Test text is
observed through the HTML editor's accessibility node. Clipboard preparation and
Copy verification are performed only by the test process with public sentinels.

Three public Rune-key scenarios cover:

- paired Shift selection, native Cut/Paste, Home/End, Select all and Copy;
- unknown pasted text followed by a literal adjacent teh suffix, then a new Rune
  Space and a successfully qualified teh → the correction;
- vertical movement at a fixed monospace column, Home/End, selection across a
  newline, and ordinary movement after turning selection mode off.

No production keyboard change was required for these cases. The test driver
performs one explicit tap on the visible HTML editor before waiting for Rune;
a page-load showSoftInput request can precede window focus and is not readiness.

Validation:

- 1,226 JVM tests pass, no failures/errors/skips. IME/scoring boundary, release
  privacy, debug lint and debug/test APK builds pass.
- Three focused WebView scenarios pass. The final integration group also passes
  all ten scenarios: those three, six existing EditText panel cases and the
  embedded-preview case. All six payload counters remain zero in the WebView
  scenarios. This is Android 36 arm64 with com.google.android.webview
  133.0.6943.137, not Samsung/Fold or every browser/provider version.
- The initial build failed on a ScrollView-only inset-helper parameter; it now
  accepts View while preserving the existing inset behavior. The first native
  run stopped at a legacy screen selector. A later run passed editor commands
  but its second setup did not show the IME. Both native failures are retained;
  neither is a behavioral pass. The current driver explicitly observes its own
  WebView status element and taps the editable node before typing. Final
  integration also checks the former EditText and preview paths.
- The ordinary 12,000-row replay is reused by exact current identity of all 88
  compilation sources, 18 runtime assets and its driver. These debug/native-test
  additions are outside that harness; no new replay execution is claimed.
  Existing EN precision/volume limitations and ES holdout's one aggregate false
  change remain. Zero new differences does not establish full qualification.
- The isolated test emulator was stopped/deleted. No physical Fold actions,
  installation, owner clipboard access, remote page loading or model scoring.

U8 remains open for Compose, Fold and manual TalkBack. Framework metadata is not
universal logical editor identity and the RAM boundary flag has no service-restart
handoff. WebView acceptance here proves the listed fixed offline textarea cases
only. The adjacent JSON binds exact sources, APKs, failed/final logs, provider
observation, replay reuse and cleanup.
