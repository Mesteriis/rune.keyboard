# Расширенный поиск ручных подсказок

## Что изменено

Добавлен выключенный по умолчанию переключатель расширенного поиска русских
подсказок. Клавиатура собирает до семи проверенных вариантов и передаёт их
существующей персонализации, CatBoost и компактной контекстной модели в зависимости
от включённых настроек. В строке остаются исходное слово и две подсказки.
Переключатель сохраняется, отключается общей командой отключения дополнительных
функций и отражается в configured/effective диагностике. Старые экспорты schema6
по-прежнему читаются анализатором; смешанные и произвольные наборы флагов отвергаются.

Базовые три кандидата, входы модели автоматической коррекции и сертификат полного
поиска на расстоянии одной ошибки хранятся отдельно. Дополнительные варианты
доступны только по ручному выбору. Действуют проверки владения редактором, актуальности
ответа, языка, защищённых/правильных слов и отмены запроса.

`CandidateGenerator.generateManualPool` повторно использует готовый неполный по
ширине, но полностью найденный набор. Иначе выполняет дополнительный поиск шириной
семь с прежним радиусом: одна ошибка для слов короче пяти символов, две — для более
длинных. В объединении сохраняются базовые варианты даже при исчерпании бюджета.
Каждый проход ограничен 8192 состояниями и 64 проверками терминальных слов;
максимум для двух проходов — 16384/128. Поиск и загрузка словарей выполняются вне
потока интерфейса. Дополнительный проход увеличивает задержку получения подсказок.

## Независимая проверка качества

Новый набор: 1500 синтетических опечаток и 300 правильных слов из 341 ранее не
использованной статьи публичного снимка Wikipedia 20231101. Пропущены первые 10880
статей, просмотренные предыдущими экспериментами. Проверены SHA-256 источников,
отсутствие пересечения статей/контекстов и точное число ошибок по метрике
optimal-string-alignment. Число ошибок — свойство синтетического теста, а не
универсальная оценка всех реальных опечаток.

Конфигурация зафиксирована после диагностического сравнения и до раскрытия
итоговой выборки. Веса CatBoost и контекстной модели не менялись. Личные диалоги
не использовались в этом эксперименте; оценки персональной истории и касаний нулевые. Метрики ниже относятся к двум
лучшим вариантам по CatBoost + REC2 на наблюдённых наборах; это не полное
воспроизведение редактора, LLM-ранжирования и интерфейса. При равных оценках
сохранён порядок набора, тогда как живой контроллер может использовать порядок
базовой политики. Это ограничение нужно учитывать при переносе цифр на телефон.

| Ошибок | Примеров | Слово в наборе, до → после | Первый вариант, до → после | В двух подсказках, до → после |
| --- | ---: | ---: | ---: | ---: |
| 1 | 600 | 565 → 580 | 558 → 571 | 565 → 580 |
| 2 | 600 | 327 → 359 | 265 → 258 | 304 → 307 |
| 3 | 300 | 0 → 0 | 0 → 0 | 0 → 0 |
| Всего | 1500 | **892 → 939** | **823 → 829** | **869 → 887** |

Это прирост покрытия на 47 примеров и появления правильного слова в двух
подсказках на 18 примеров (1,2 процентного пункта). Для двух ошибок первый вариант
ухудшился на семь примеров: текущий ранжировщик обучался на более узком наборе.
Поэтому расширение оставлено отдельным экспериментом, выключенным по умолчанию.
Для правильных слов дополнительный набор не менялся; базовая локальная политика
не предложила замен в 300 контрольных случаях. Это не оценка частоты ложных
автозамен на реальном пользовательском вводе.

На ранее раскрытой выборке покрытие выросло 907 → 952, первый вариант остался
816, попадание в две подсказки выросло 888 → 897. Все 1800 базовых генераций и
предложений локальной политики побитово совпали с сохранёнными наблюдениями до
этой задачи (времена выполнения исключены).

### Почему не включён радиус три

Отдельная проба в копиях исходников расширяла радиус до трёх для неизвестных слов
длиной от семи символов при тех же бюджетах. На диагностической выборке покрытие
выросло до 986, но правильный первый вариант упал с 816 до 770, а попадание в две
подсказки — с 888 до 879. Проба отвергнута до итоговой проверки. Три ошибки в
производственной версии по-прежнему не покрываются этим поиском.

## Производительность и проверки

На хосте, на новой выборке, p95 поиска вырос с 2,06 до 4,13 мс с дополнительным
проходом. Это измерение JVM на Mac; оно не включает ранжирование, загрузку,
редактор и отрисовку и не заменяет проверку телефона.

На принадлежащем этой задаче эмуляторе Android API37: 200 прогретых запросов,
10 синтетических слов, 20 прогревочных запросов. p95 базового поиска — **19,34 мс**,
двух проходов — **38,59 мс**, поиска вместе с CatBoost + REC2 — **39,78 мс**.
Максимум последнего — 42,64 мс. Расширение сработало на 120/200 запросов,
максимальный набор — семь слов. Загрузка словарей/моделей, очередь запросов,
редактор и отрисовка исключены. Это эмулятор, не измерение физического телефона.

Цена расширения — примерно ещё 19 мс p95 на этом стенде. Ограничение работы
сохранено, но ускорением поиска это изменение не является. Оно оставлено как
опциональный способ повысить покрытие; включение по умолчанию не разрешалось.

Проверки: **963 JVM**, **33 Android**, **6 Python для нового сравнения** и
**49 Python для диагностики/границ** — без ошибок. На окончательном APK повторно
прошли шесть тестов настройки/общего отключения/поиска и снят указанный benchmark.
`lintDebug`, `imeIntelligenceBoundary`, `forbiddenRuntimeDependencies`,
`privacyGateRelease`, сборки приложения и androidTest прошли. Первичные падения
проверки словаря диагностических флагов и отсутствующих переводов исправлены;
исходные логи с ненулевыми кодами сохранены.

APK: `build/typing-retrieval/rune-candidate-retrieval-debug.apk`, 282241247 байт,
SHA-256 `6ea6aff55b67c7a2cdfcfc49b3399d3249f823a4ae5657a0d3d9fb1263787942`.
На личный телефон APK не устанавливался.

## Воспроизведение и доказательства

Рабочий каталог: существующий worktree `build/worktrees/morphology-style`.
Все данные, исполняемые артефакты, сырые логи и результаты находятся в игнорируемом
`build/typing-retrieval`; приватные данные не добавляются в git.

- `prepare_retrieval_test.py`: новый публичный набор, фиксированные квоты и проверки
  источника/предыдущих манифестов; нужен локальный PyArrow.
- `export_retrieval.py`: компиляция реального Kotlin-поиска, хеши исходников,
  словарей и инструментов. Наблюдатель получает только введённое слово, без
  правильного ответа или контекста.
- `evaluate_retrieval.py`: неизменённые CatBoost/REC2, покрытие и top-1/2/3 с
  отсутствующим правильным словом в знаменателе; итоговый запуск требует
  зафиксированных конфигурации и манифеста.
- `selection.json`, `fresh.json`, `diagnostic-final.json`, `baseline-parity.json`,
  `data-integrity.json`: решения, метрики и проверки целостности.
- `radius3-probe/`, `probe_radius3.py`, `score_radius3.py`,
  `radius3-diagnostic.json`: отвергнутая проба и точные копии её исходников.

Пример команд после подготовки локального окружения:

```sh
PYTHONDONTWRITEBYTECODE=1 build/morphology-venv/bin/python tools/typing_experiments/export_retrieval.py \
  --rows build/typing-retrieval/data/test-rows.jsonl --output build/typing-retrieval/reproduction
PYTHONDONTWRITEBYTECODE=1 build/morphology-venv/bin/python tools/typing_experiments/evaluate_retrieval.py \
  --export build/typing-retrieval/reproduction --output build/typing-retrieval/reproduction.json \
  --fresh-manifest build/typing-retrieval/data/manifest.json --selection build/typing-retrieval/selection.json
```

Повторное выполнение уже раскрытой итоговой выборки является воспроизведением,
а не новой независимой проверкой. Для изменения радиуса, состава набора или
ранжировщика нужна отдельная выборка.
