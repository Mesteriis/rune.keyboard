# Short-frequency candidate policy: scoped review

2026-09-06. Reviewed the build-only `short-frequency-01` patch, probe report, summary and oracle summary against the candidate, ranking and qualification contracts at baseline `6f7c35e`. No holdout rows were read. No model, Gradle, device, network, implementation or nested-agent work was performed. This report is the only review write.

## Decision

**Sound as a bounded retrieval-policy hypothesis; suitable to proceed to exact-policy evaluation, not yet to automatic production adoption.** The two-line semantic change does not establish a search/certificate correctness defect. The reported net recall gain is useful evidence for evaluation, not a passed precision gate.

The short-query branch bypasses `selectTop`, whose certificate assumes cost-first order, and instead completes the existing UNIT-radius-one scan before applying prior/frequency-first order. It therefore does not misuse a cost-order top-N certificate for a frequency-order result. The exhaustive reader contract supports selection under a different comparator after complete enumeration. Partial scans preserve exhaustion and its automatic veto. Protection, valid membership, casing, deduplication, quota, width and shared search/verification limits remain intact.

The oracle's 189 matching COMPLETE short queries supports this interpretation. It does not qualify incomplete scans, model ranking, controller writes, canonical-case behavior, physical latency or all possible queries. The 39 gains and five losses and unchanged long outputs/statuses are meaningful calibration observations, not evidence that every changed short query improves.

## Adoption risks to carry forward

- Frequency becomes decisive before edit cost for short queries. The five reported lost targets are expected policy tradeoffs, not noise to remove. Language prior also moves ahead of edit cost: a primary-language candidate can displace a closer fallback. Preserve mixed-language negatives and all losses in evaluation.
- An unchanged radius/status does not preserve automatic decisions. Different rivals, candidate IDs/order and model scores change confidence margins. Native scoring uses the candidate set's common token prefix; do not splice an old candidate's score into a changed request, even when that candidate text is unchanged. Reuse only independently validated exact full request identities, or simply rescore.
- Current RU/ES minimum token lengths are five, so ordinary short NFC words cannot auto-replace under those coefficients; English minimum length is one. This is not permission to omit RU/ES evaluation: retrieval branches on folded scalar length, while `CandidateRanker` measures the original's scalar length. Decomposed marks can make those lengths differ, and suggestions change in all three languages.
- The current class is `SpellingQualification`, not `SpellingAutoReplaceQualification`. Its `CURRENT` lambda admits model-assisted spelling for every language without identifying the retrieval policy. Applying the patch to production would immediately expose the new sets to that old permission. Keep the variant isolated until acceptance, or explicitly disable automatic admission for the experimental policy; do not present the old lambda as new qualification.
- `CandidateGenerator.kt:63` documents unconditional cost-first proposal order. Adoption must update that contract to describe the short/long split, without changing `PackedTopSeven`'s existing comparator/certificate semantics.

## Smallest legitimate evaluation and adoption route

1. Freeze one exact candidate policy, unchanged assets/model, width three, 8192/64 controls, and existing `CalibratedSpellingPolicy` coefficients and thresholds. A coefficient refit is **not mandatory**: evaluating whether the existing coefficients remain acceptable on the new sets is the smaller first experiment. Select or revise policy only using calibration; retain the present losses.
2. Export and score actual new-policy controller requests on calibration, with full canonical-case/controller behavior and source/request identities. Confirm deterministic/model paths, false changes, Original, exact Undo, model failures and abstentions. The generator-only probe's empty canonical lexicon cannot supply this evidence. If calibration warrants any coefficient change, choose it there and freeze the resulting configuration before final evaluation.
3. Use a distinctly named/versioned **changed-policy evaluation** protocol. `final_product_replay.py` currently hardcodes `revealed-data-fixed-policy-reproduction`, `unchanged-policy-freeze`, `policyChanged: False`, and old configuration/qualification bindings. Do not run that unchanged protocol and call its receipt new-policy qualification. Preserve old artifacts; add an explicit new-policy identity/provenance record and only the narrowly necessary protocol checks/fixtures, retaining strict cache/source/coverage verification.
4. Evaluate the frozen policy against the complete agreed corpus with actual controller outcomes: per-language 95% point precision, at most 0.5% correct/protected false changes, existing minimum 300 automatic spelling changes, Original retained wherever a word set exists, and exact Undo. Report changed-subset outcomes and the five known losses alongside totals; do not change denominators, omit abstentions or tune on final results. Also verify suggestions and model-unavailable fallback.
5. The existing corpus has already been revealed. Fresh scoring of this new policy may support **revealed-data product acceptance under the user's agreed gates**, but cannot be described as unseen qualification. No new corpus is inherently required merely because this policy changed. A genuinely unseen qualification claim would require an independent untouched set and a predeclared protocol. If final results fail, preserve them; do not iteratively select on that result while maintaining an unseen claim.
6. Only if the agreed measured gates pass, promote the frozen implementation and update the qualification/configuration comments and acceptance record to cite this exact retrieval policy and evidence. No broader qualification framework is needed just for this two-line change. Run the ordinary source/JVM/privacy/build checks and focused API candidate/controller verification appropriate to the changed scan path; measure short-query latency because the probe already shows additional work. Physical and release gates remain separately required.

`автокрекция` and `correcion` are outside the changed length class and remain unresolved named retrieval limitations. Do not combine another experiment, force either target, or claim whole-milestone completion from adoption of this policy.
